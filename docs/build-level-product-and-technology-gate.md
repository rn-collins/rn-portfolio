# Build-Level Product & Technology Gate

Status: controlling gate for every numbered A/B cycle before public-canon freeze and before release.

## Core principle

**Maximum warranted technical sophistication behind the interface; minimum necessary cognitive burden in front of it.**

A numbered build is not admitted merely because the topic is interesting or the engineering is difficult. It must become a consumer-facing product that a nontechnical visitor can understand and use without specialized education, while the implementation underneath should be as technically ambitious, rigorous, and reusable as the problem genuinely warrants.

## A-side admission gates

### 1. Immediate comprehension
A first-time visitor should be able to answer within moments:
- What is this?
- Is this for me?
- When would I use it?
- What do I need to provide?
- What will I get back?

No technical vocabulary may be required to use the primary path. Domain-specific terms must be explained in context or moved behind progressive disclosure.

### 2. Ease of adoption
- useful first value without an account unless identity is genuinely necessary;
- no unnecessary setup, integrations, uploads, or configuration before first value;
- structured defaults and examples before free-form complexity;
- novice/default path plus deeper expert controls when warranted;
- save, copy, export, share, or return path appropriate to the artifact;
- mobile and keyboard usability treated as primary rather than secondary.

### 3. Consumer-facing value
The output must help someone make a decision, understand a system, produce something usable, diagnose a problem, compare options, plan an action, or discover something they could not readily obtain from a static article/checklist.

### 4. Accuracy and evidence
- research/factual basis is traceable;
- scoring and recommendations are explainable;
- uncertainty and limitations are visible;
- legal/scientific/health/regulatory tools do not disguise heuristics as certification or professional advice;
- outputs distinguish fact, inference, model judgment, and user-supplied assumptions when relevant.

### 5. Technical ambition
For every build ask: **what is the most capable technically defensible version of this product that materially improves the user's outcome?**
Potential capabilities include, only when warranted: structured data models, provenance, retrieval, graph systems, geospatial analysis, optimization, simulation, multimodal input, local-first processing, agents, orchestration, real-time data, APIs, interoperability, versioning, evaluation, personalization, accessibility adaptation, and explainable recommendation engines.

Do not add technology for spectacle. Do not avoid advanced technology merely to keep the implementation simple. Complexity belongs behind the interface.

### 6. Progressive disclosure
Primary experience should be usable by a smart general reader. Advanced controls, methodology, source inspection, assumptions, data provenance, confidence, settings, and expert modes can unfold as the visitor asks for depth.

### 7. Accessibility and educational independence
The product must not assume software-engineering knowledge, graduate education, legal training, scientific literacy, or familiarity with RN's prior work. Plain-language framing and examples must coexist with rigorous underlying architecture.

### 8. Actionability
Results must answer 'what now?' The user should leave with prioritized next steps, a decision, a usable artifact, a map, an assessment, a comparison, or a clearly stated unresolved question.

### 9. Distinct reason to be software
If a static article, checklist, spreadsheet, or PDF could deliver essentially the same value, either redesign the build to exploit computation/interactivity or do not spend a numbered A slot on it.

### 10. Compounding infrastructure
Every A should create or deepen reusable capability where technically sensible. Reuse must be real: shared package, schema, data model, service, evaluator, primitive, API, or workflow—not a lineage label with no implementation connection.

## B-side admission gates
B remains a separate built artifact. It must stop attention, communicate the proposition silently, leave an intellectual souvenir worth saving, and create a legitimate reason to experience A. Motion, data, spatial interaction, creative code, film, UI choreography, or another medium should be chosen because it reveals the mechanism, not because animation is fashionable.

## Pair gate
A and B must function as two interfaces to one intellectual object:
**B makes the problem visible; A makes the problem usable/actionable.**

## Conversion gate
A retained build must plausibly support the path:
**STOP → UNDERSTAND → SAVE → CLICK → USE → RECEIVE VALUE → REMEMBER RN → CONTACT / COLLABORATE**
without turning the product into a lead-generation trap.

## Canon audit consequence
Every current and replacement build must now be audited twice:
1. **Should this problem occupy one of the 100 public slots?**
2. **Is the proposed product expression good enough under this build-level gate?**

A strong topic with a weak product expression is not approved. It must be redesigned before the canon freezes.
