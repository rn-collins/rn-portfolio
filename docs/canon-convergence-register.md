# Canon Convergence Register — 100 Builds

Status: ACTIVE / pre-freeze
Purpose: reconcile the ten deep-audit batches into one defensible Canonical 100 v1.0 before the runtime registry is rewritten.

## Non-negotiable freeze gates
A build may remain in the Canonical 100 only if it passes all of the following simultaneously:
1. Public strategic value — the problem deserves a numbered public slot.
2. Product value — the A-side is something another person can actually use.
3. Comprehension range — general-public by default; expert depth on demand.
4. Technological ceiling — A and B both reach the strongest warranted implementation feasible at build time.
5. A/B integrity — B explains or lets the visitor experience the same underlying idea as A.
6. Distinctness — the public job is not substantially duplicated by another build.
7. Sequence value — the build either creates reusable capability or meaningfully consumes earlier capability.
8. Evidence/limits — consequential claims expose provenance, uncertainty, assumptions, and boundaries.
9. Public-transfer value — Behind the Build / Method teaches something another person can reuse.
10. Exhibition fit — it can be shown as USE + B-Web + B-MP4 + WHY + MAKING + METHOD + EVIDENCE + LINEAGE + VERSIONS + PRACTICE.

No title, phase, number, or runtime record is considered frozen until this convergence pass is complete.

# D. Gap register — areas the final 100 must demonstrate before freeze
The converged canon must show credible coverage of:
- approachable consumer/public utilities, not only enterprise/governance tools;
- law/transaction/regulation and not only AI governance;
- neuroscience/neurotechnology without overstating evidence;
- cannabis and psychedelic systems with medical/legal boundaries;
- place/Hawaiʻi/island systems;
- creators / Institutions of One / ownership / IP;
- evidence, research, journalism, provenance;
- privacy, consent, accessibility, comprehension;
- real-time systems and orchestration;
- geospatial computation;
- simulation/optimization;
- local-first/offline systems;
- multimodal input;
- knowledge/provenance graphs;
- agents and agent evaluation/governance;
- advanced creative technology across B-Web;
- interoperability and data portability;
- public-interest / community governance;
- longitudinal/personal systems with user control;
- decision-support systems that expose uncertainty and tradeoffs.

Potential underrepresentation to test in the final balance audit:
- transactional business/legal decision tools (contracts, ownership, deal structures) relative to regulatory systems;
- physical-world / hardware / sensor / spatial-computing builds beyond smart environments;
- direct public tools unrelated to regulated sectors, to prevent the canon from reading too institutionally;
- collaborative/multi-user products rather than mostly individual diagnostics;
- financial/economic modeling that is not merely business analytics;
- accessibility technologies as working interactions rather than checklists;
- multilingual/cross-cultural interaction as actual runtime capability.

These are gap hypotheses, not automatic additions. Any new candidate must defeat an incumbent rather than push the total above 100 unless the convergence audit concludes 100 itself is structurally insufficient.

# E. Sequencing rule
The final order is **not simply easiest to hardest** and not simply domain-clustered. It must satisfy four constraints:
1. each build reaches its own local technological ceiling;
2. dependencies needed by a build exist before that build where practical;
3. the public series varies domains enough that it does not feel like ten consecutive versions of the same idea;
4. technical capability visibly compounds across the 100.

Build 001 remains fixed unless convergence discovers a fatal reason to replace it. Build 100 remains the intended culmination unless another end-state proves stronger.
