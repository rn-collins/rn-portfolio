# Public Accession Content Model

Every numbered build uses the same public architecture while allowing its actual product and visual mechanism to differ.

## Accession-level fields
- id / accession number
- title
- public question
- one-sentence plain-language purpose
- status
- domains / field intersections
- A-side label and route
- B-side label and route
- intended first-value time
- education-range target
- evidence status
- lineage parents
- infrastructure created
- related works
- practice relevance

## Public sections
### VIEW
What this is, why it exists, A/B objects, status, central question. Must be legible without domain expertise.

### USE — A
The functional product. Product UI gets its own appropriate design while remaining inside the Exhibition world. No build-process notes inside the task flow.

### WATCH / EXPLORE — B
The bespoke visual argument. Medium chosen per idea: kinetic type, data animation, interactive editorial, map, UI choreography, real footage, WebGL, etc. B is not required to look like another B.

### WHY
Observation, tension, audience/problem, and research question. Explain why this deserved software rather than a PDF/article.

### MAKING
Public build history: meaningful iterations, wrong turns, user-comprehension changes, technical decisions that another person can learn from. Internal instructions must be translated before publication.

### METHOD
Reusable principles extracted from the project. Include a “use this in your own work” treatment when warranted.

### EVIDENCE
Research basis, source hierarchy, methodology, assumptions, uncertainty, limitations, dates/jurisdictions where relevant. Evidence cannot be collapsed into a confidence aesthetic.

### LINEAGE
What the build inherited, what it created, where its infrastructure is actually used later. Only real code/schema/process inheritance is shown as technological lineage.

### VERSIONS
Meaningful public version history. Explain what changed and why; do not expose routine dependency bumps or irrelevant operations.

### PRACTICE
Contextual conversion. “Facing a related systems problem?” followed by the relevant way RN can help. No generic hire-me banner in the middle of the user task.

## Internal-only record
The public model does not include acceptance gates, secret keys, deployment procedures, raw commercial hypotheses, internal analytics targets, private client/source information, test fixtures containing sensitive data, unresolved security findings, or production credentials. Those stay in Lab Records / issues / tests.

## Accessibility and education-range rule
Every public section must have an understandable top layer. Technical/professional terms can appear when needed, but either become clear from context or have an immediately available explanation. The default visitor is not assumed to have a degree, technical training, legal education, scientific training, or knowledge of the series.

## Design rule
The Exhibition metaphor structures navigation and information; it may never make a functional product harder to use. When gallery aesthetics conflict with usability, the task wins.
