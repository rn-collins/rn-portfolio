# Final Build Admission Records — 001–010

Controlling rule: **maximum warranted technical sophistication behind the interface; minimum necessary cognitive burden in front of it.**

Each record tests: public value, product worthiness, education-range comprehension, technical ambition, A/B pair integrity, saveability, conversion, and lineage contribution.

## 001 — Human Review Design Framework
**Verdict:** KEEP / anchor build.
**Public question:** Is the human actually able to catch or stop a bad AI-assisted decision?
**Primary user path:** No AI/governance knowledge assumed. Choose a familiar use case; answer plain-language questions about who checks the AI, when they check it, what they can see, whether they can say no, and what happens when something is wrong. Receive a prioritized diagnosis.
**Education-range test:** A motivated middle-school learner should understand the core choices; a professional can open deeper design fields and evidence notes.
**Expert depth:** role qualification, timing, evidence sufficiency, authority, escalation, auditability, capacity, control testing, consequence-aware recommendations.
**Technical ceiling:** deterministic rules now; later scenario presets, provenance-linked guidance, configurable domain rule packs, versioned assessment logic, exportable review protocol, evaluation telemetry that does not collect sensitive workflow data by default.
**Must not require:** knowledge of HITL, AI governance, EU AI Act, NIST, compliance, risk taxonomies, or software architecture.
**Saveable payload:** meaningful review architecture and prioritized fixes.
**B-side job:** make “human in the loop” visibly fail when presence lacks power.
**Conversion:** related AI workflow / governance design problem → Practice.
**Lineage:** form engine, conditional logic, results renderer, progressive disclosure, consequence-aware recommendation pattern, visual-reveal primitive.

## 002 — Multi-Audience Messaging Architecture
**Verdict:** REFRAME / keep only as a public translation product, not a messaging worksheet.
**Public question:** How do you explain the same true thing to very different people without changing the truth?
**Primary user path:** Paste one core claim or explanation; choose 2–4 audiences (e.g. teenager, customer, regulator, investor, patient, lawyer); receive audience-specific versions plus a visible “truth preserved / changed / unsupported” comparison.
**Education-range test:** users need only understand their original point and who needs to hear it. Include examples before jargon.
**Expert depth:** claim decomposition, audience constraints, register, risk-sensitive language, prohibited shifts, terminology preservation, uncertainty markers.
**Technical ceiling:** structured claim graph + audience profiles + constrained generation + semantic consistency checks + diff visualization + provenance of transformations.
**Must not require:** communications theory, prompt engineering, linguistic terminology.
**Saveable payload:** the “same truth, different doors” comparison and translation checklist.
**B-side job:** one sentence travels through several doors and changes form while its factual core remains fixed.
**Conversion:** communication architecture, science/legal/technical translation, public-facing complex systems work.
**Lineage:** audience profile schema, claim-preservation rules, comparison/diff component.

## 003 — Unserved Decision Discovery Framework
**Verdict:** KEEP / strengthen consumer utility.
**Public question:** Where are people drowning in information but still missing the tool that helps them decide?
**Primary user path:** Describe a recurring situation; choose what people currently have (articles, spreadsheets, experts, dashboards, forums) and what they still cannot decide; receive a “decision gap” map and product opportunity hypotheses.
**Education-range test:** examples should include everyday choices, not only startup/product language.
**Expert depth:** frequency, consequence, ambiguity, fragmentation, buyer/user split, existing substitutes, evidence burden, monetization only as optional layer.
**Technical ceiling:** decision ontology + clustering + unmet-decision scoring + evidence/search integration + opportunity comparison.
**Must not require:** product-management terminology or business education.
**Saveable payload:** information ≠ decision framework.
**B-side job:** a crowded information field collapses around an empty decision point.
**Conversion:** product discovery / systems research engagements.
**Lineage:** decision inventory schema, opportunity scoring primitive.

## 004 — Manual Intelligence Engine Method
**Verdict:** KEEP if framed as “build the intelligence process before automating it.”
**Public question:** What should a reliable research/intelligence process look like before AI or automation touches it?
**Primary user path:** Pick a question; the tool walks through source collection, verification, contradiction, update cadence, decision output, and handoff.
**Education-range test:** use “what are you trying to know?” before “intelligence requirement.”
**Expert depth:** source tiers, freshness, uncertainty, verification queues, contradiction handling, evidence state, collection gaps.
**Technical ceiling:** source ingestion + verification workflow + provenance graph + change detection + structured brief generation.
**Must not require:** intelligence-analysis vocabulary or coding.
**Saveable payload:** trustworthy intelligence loop.
**B-side job:** messy manual research becomes a disciplined chain, then becomes automation-ready.
**Conversion:** research systems / evidence operations.
**Lineage:** collection protocol, verification queue, evidence-state model.

## 005 — Service-to-Software Discovery Engine
**Verdict:** KEEP / high commercial relevance.
**Public question:** Which parts of a service should become software—and which absolutely should not?
**Primary user path:** Describe a service in normal language; break it into repeated steps using guided prompts; tool marks steps as automate, assist, keep human, or remove, with reasons.
**Education-range test:** no need to know workflows, APIs, agents, or automation categories.
**Expert depth:** variability, judgment, consequence, reversibility, data availability, frequency, latency, customer trust, regulatory constraints.
**Technical ceiling:** process decomposition + task classification + constraint/risk scoring + automation pattern recommendations + dependency graph.
**Must not require:** process engineering or software knowledge.
**Saveable payload:** automate / assist / human / eliminate matrix.
**B-side job:** a service literally separates into four paths.
**Conversion:** AI implementation, productization, workflow redesign.
**Lineage:** service decomposition schema, automation suitability engine.

## 006 — Tracker-to-Company Productization Framework
**Verdict:** REFRAME to broader “Is this tool actually a product?”
**Public question:** You made a tracker, database, checklist, or internal tool. Is there actually a product here?
**Primary user path:** choose what you built and who uses it; answer simple questions about recurring need, maintenance, unique data/logic, willingness to switch/pay, and whether value grows with use; receive product/service/content/internal-tool recommendation.
**Education-range test:** avoid startup jargon such as moat/TAM in default mode.
**Expert depth:** buyer-user split, defensibility, switching, data rights, market structure, operational burden, recurring value.
**Technical ceiling:** evidence-backed classification + comparable archetypes + scenario economics + defensibility map.
**Must not require:** venture/startup education.
**Saveable payload:** “not every tracker is a company” decision tree.
**B-side job:** a tracker passes through gates and emerges as product, service, content, or internal infrastructure.
**Conversion:** product strategy / venture ideation.
**Lineage:** productization gate engine, buyer-value model.

## 007 — Feedback Loop Product Architecture
**Verdict:** KEEP / make concrete.
**Public question:** Does your product actually learn from what happens after people use it?
**Primary user path:** choose a product/service; answer what happens after use, what corrections occur, what outcomes are visible, who reviews feedback, and whether changes are measured; receive a feedback-loop diagram and missing links.
**Education-range test:** frame around “what happens next?” rather than analytics terminology.
**Expert depth:** event taxonomy, qualitative/quantitative signals, adjudication, causal caution, feedback abuse, privacy, experiment design.
**Technical ceiling:** governed feedback ingestion + event/outcome joins + feedback triage + experimentation/evaluation loop.
**Must not require:** analytics, ML, or product ops knowledge.
**Saveable payload:** product learning loop.
**B-side job:** one-way arrow closes into a loop only when outcomes and corrections return.
**Conversion:** adaptive product / measurement architecture.
**Lineage:** feedback event schema, improvement-loop primitive.

## 008 — Decision-Ready Dashboard Standard
**Verdict:** KEEP / public-facing diagnostic.
**Public question:** Is your dashboard helping someone decide—or just showing them things?
**Primary user path:** upload/screenshot or describe a dashboard; identify who sees it and what decision they need to make; receive a decision-readiness diagnosis and redesign priorities.
**Education-range test:** first screen asks “what should someone be able to decide after looking at this?”
**Expert depth:** decision ownership, thresholds, action states, uncertainty, provenance, latency, alerting, drill-down, competing objectives.
**Technical ceiling:** multimodal dashboard parsing + chart/metric extraction + decision-model matching + accessibility checks + redesign suggestions.
**Must not require:** data visualization training.
**Saveable payload:** data → signal → decision → action model.
**B-side job:** a wall of charts reduces to the one decision the dashboard should support.
**Conversion:** dashboards / decision-support / information design.
**Lineage:** decision-readiness rubric, action-state component.

## 009 — Place-Sensitive Technology Readiness Tool
**Verdict:** KEEP / replaces generic Aloha AI principles slot.
**Public question:** A technology works somewhere else. What has to be true for it to work here?
**Primary user path:** choose technology + place; answer understandable questions about connectivity, cost, workforce, law, language, culture, geography, accessibility, maintenance, and local trust; receive blockers, adaptations, and unknowns.
**Education-range test:** usable by community member, student, policymaker, founder, or engineer; define technical terms inline.
**Expert depth:** geospatial constraints, regulatory metadata, infrastructure dependencies, demographic/access layers, local procurement/maintenance, implementation evidence.
**Technical ceiling:** geospatial data + dependency graph + public datasets + regulatory/location retrieval + scenario engine + uncertainty display.
**Must not require:** GIS, policy, engineering, or planning expertise.
**Saveable payload:** “works elsewhere ≠ works here” readiness map.
**B-side job:** a technology crosses a map and encounters place-specific constraints that physically reshape it.
**Conversion:** implementation research / place-sensitive technology strategy.
**Lineage:** constraint matrix, place profile schema, geospatial readiness primitive.

## 010 — Canonical Data Model & Schema Designer
**Verdict:** REFRAME / keep if user-facing as “turn a messy idea into a clean structure.”
**Public question:** You know what your system is about, but what exactly are the things, fields, relationships, and rules inside it?
**Primary user path:** describe the thing in normal language or paste a messy spreadsheet/form; tool proposes entities, fields, relationships, required/optional data, examples, and ambiguities.
**Education-range test:** never lead with entity/schema/normalization terminology; teach terms after showing the structure.
**Expert depth:** types, constraints, cardinality, provenance, versioning, controlled vocabularies, validation, identifiers, interoperability.
**Technical ceiling:** LLM-assisted structure extraction + schema inference + validation + graph preview + sample data generation + export to JSON Schema/SQL/CSV templates.
**Must not require:** databases or software engineering.
**Saveable payload:** before/after “idea → structure” visual.
**B-side job:** loose notes snap into a visible skeleton of things and relationships.
**Conversion:** data/product architecture.
**Lineage:** schema builder, validation rules, data dictionary primitive.
